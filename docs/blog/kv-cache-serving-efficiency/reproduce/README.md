# Reproducing the measurement

## Doing this for your own workload (Section 6 of the post)

Four steps, each one script or one job, give η and its split for any workload on any deployment.

1. **Characterise the trace.** From the per-request records: mean input and output lengths I and O, turns per session and the pause between them, and ρ from an oracle replay in which every prefix stays cached. Count ρ over the whole trace, each session's first turn included.
2. **Calibrate the deployment.** Two jobs on one replica: prefill throughput at the trace's context, and the decode KV-read rate from the step-time difference between one and four long-context decodes. With KV bytes per token, HBM available for KV and weight bytes per step, that is all R needs (Appendix A).
3. **Compute R and what binds.** The closed form of Appendix B, or the step-time law iterated over the batch. If capacity binds, note the batch at the wall and the KV the paused sessions need outside HBM: turn rate × pause × context. That number sizes a host tier before one is bought.
4. **Sweep the load and split the shortfall.** Run an ascending ladder of session counts; at each level take the steady window and record the hit rate in every tier, HBM occupancy, running and waiting requests, preemptions, step rate, and per-request Z and T. η is the peak over R; client, reuse and engine follow from Section 3.

The split then names the lever:

| What you see | Factor | Lever |
| --- | --- | --- |
| Hit rate well below ρ while HBM is far from full and nothing is preempted | Reuse | Routing: turns land on replicas that do not hold their context. Fix the index or the affinity before adding memory. |
| Hit rate holds at low load and falls as sessions are added, with HBM filling | Reuse, then engine | Retention: paused sessions are being evicted. A host tier, or fewer sessions per replica. |
| Hit rate holds, HBM near full, preemptions, step times growing | Engine, from capacity | More HBM for decoding KV: fewer bytes per token, shorter contexts, a tier for everything not decoding. |
| Hit rate holds, HBM half empty, requests waiting, step times above the law | Engine, from scheduling | Chunk size and admission: prefill chunks stalling decodes, tier copies in the critical path. |
| Sessions idle beyond their tool pause, few requests in flight | Client | The load generator, not the stack. Fix it before concluding anything. |
| All three factors near one and η still low | The ceiling | The hardware is what it is. Compare deployments, not stacks. |

Section 5 is this procedure applied once.

## Scripts, by step
Everything used for the post, arranged by the four steps of its Section 6. Paths below are relative to this folder. Set `KUBE_CONTEXT` (and `NAMESPACE`, default `kv-fleet`) before running anything that talks to a cluster.

## 1. Characterise the trace

The trace is generated by inference-perf's conversation replay from `harness/config.template.yaml` (shared 3,000-token system prompt, lognormal per-conversation prefix, 20 turns, lognormal tool pause). After a run, the per-request records give the workload's numbers:

- `analysis/oracle_chars.py <run dir>`: ρ, the hit rate an unlimited-retention cache reaches, over the whole trace. Character blocks stand in for tokens.
- `analysis/round2_inputs.py <out.json>`: per run, mean prompt and output length, tool pause, idle beyond the pause, engine time per turn, sessions in flight, requests running and waiting. Edit `RUNS` at the top for other runs.

## 2. Calibrate the deployment

One replica, same flags as the fleet.

- Prefill throughput at 8k, 32k and 128k context: the llm-d router's peak-prefill calibration job (chunk size over median time to first token for cache-missing prompts); the values used are in `calibration/b200_calib_summary.txt`.
- Decode KV-read rate: `calibration/decode_calib.py` with `VLLM_ENDPOINT`, `MODEL_NAME` and `CASES=1024:1,131072:1,131072:4`. The read rate is the extra KV bytes per step between one and four 131k-token decodes, divided by the extra step time; divide by the datasheet bandwidth for α_W.
- KV bytes per token: `kv_offload_load_bytes_total / external_prefix_cache_hits_total` on any replica with the host tier on, or the model shape (2 × layers × KV heads × head dim × bytes).

## 3. Compute the ceiling

`analysis/ceiling_v2.py` prints R per GPU and per fleet, the batch at which capacity binds, the compute share there, the paused-session KV the host tier must hold, the ideal throughput-against-batch curve, the two capacity walls, the Section 7.1 thresholds and the rule check. Hardware constants are in `analysis/ceilings.py` (`HW` table) and at the top of `ceiling_v2.py`; the workload's I, O and ρ are set there too. The expert-weight term counts every token in a step, decode and prefill alike.

## 4. Sweep the load and split the shortfall

Deploy (`deploy/`):

- `modelservers-offload.yaml`: six vLLM replicas with the 1.61 TB host tier. `/dev/shm` must be at least the tier size; `vllm_pin_backport.py` (mounted from a ConfigMap, run at container start) registers the tier in 64 GiB pieces, which vLLM 0.28 needs for tiers above 512 GiB under tensor parallelism.
- `router-plugins.yaml`: the llm-d router config. `lruCapacityPerServer` is in the router's own block units; without a tokenizer the router counts 4 bytes as a token, so size it from the host tier in engine blocks times the trace's bytes per token over 4.
- `dynamo-offload.yaml`, `dynamo-infra.yaml`: Dynamo workers and frontend. Keep `self_describing_kv_events` on so the router sees the host tier, and check the frontend log for `Rejected incompatible workers`: Dynamo admits only workers whose model directories match byte for byte.
- `podmonitoring.yaml`, `make_dashboard.py` (`PROJECT` env): Cloud Monitoring scrape and dashboard.

Run (`harness/`):

- `ladder.sh`: `ARM=llmd|dynamo|rr OUT_NAME=<dir> LEVELS="120 180 240" TEMPLATE=harness/config.template.yaml bash harness/ladder.sh`. One level per session count; concurrency 4 × sessions, 20 turns per conversation, 32 worker processes (the inference-perf lockstep workaround); waits for six ready replicas and checks that all six reported.
- `overnight2.sh`, `dynamo2.sh`, `dynamo3.sh`: the orchestration used, including the GPU swap to Dynamo and the admission and burst checks before its ladder.
- `sample_metrics_offload.py <csv> 15`: scrapes every replica's vLLM counters every 15 s; needed for everything in step 4.
- `fleet_check.py`: the fewest replicas reporting during a level.

Analyse (`analysis/`):

- `judge_level.py <run dir> <samples.csv> 5 0 window`: the steady window (sessions in flight at or above 90% of peak) and steady throughput.
- `offload_levels_round2.py`: per level, hit rate in HBM and in the host tier, HBM occupancy, preemptions, running and waiting requests.
- `flops_ai_offload.py <samples.csv> <t0> <t1>`: FLOP/s, HBM traffic and arithmetic intensity from the counters and the model shape; host-tier hits are not counted as recompute.
- `harness_check.py <run dir> <sessions>`: what load the harness delivered (sessions in flight, idle beyond the tool pause).
- `round2_split_v2.py <inputs.json> 253952`: the client, reuse and engine factors.

`results/` holds the per-level manifests, the summary tables and the decomposition inputs for the nine runs of the post. The per-request records (3 to 10 GB per level) are not included.
